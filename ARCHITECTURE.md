# Архитектура «ВышКат»

Итоговая структура реализации ДЗ1. Подробные правила, обоснование SOLID,
команды запуска и сценарий демонстрации находятся в [README.md](README.md).

```text
src/main/java/ru/hse/vyshkat/
├── Main.java                         # открывает Spring-контекст и запускает меню
├── config/
│   └── ApplicationConfiguration.java # связывает ServiceCenter, FleetService, меню
├── console/
│   ├── ConsoleInput.java             # разбор полей, повтор запросов при ошибке
│   └── ConsoleMenu.java              # команды и отображение результатов
├── inspection/
│   ├── ServiceCenter.java            # контракт техосмотра транспорта
│   ├── BasicServiceCenter.java       # правило исправных тормозов и целой рамы
│   └── InspectionResult.java         # решение и пояснение
├── model/
│   ├── InventoryItem.java            # название и инвентарный номер
│   ├── EnergyConsumer.java           # суточная энергия в BigDecimal
│   ├── Transport.java                # общие характеристики транспорта
│   ├── Equipment.java                # общие данные вещей
│   ├── transport/
│   │   ├── Bicycle.java
│   │   ├── ElectricBicycle.java
│   │   └── ElectricScooter.java
│   ├── equipment/
│   │   ├── Helmet.java
│   │   └── ChargingStation.java
│   └── validation/
│       └── ModelValidation.java      # общие инварианты строк и расхода
└── service/
    ├── FleetService.java             # приёмка, баланс в памяти, отчёты
    └── FleetSummary.java             # неизменяемый снимок итогов
```

Пакеты тестов повторяют области исходного кода. Полный демонстрационный ввод
лежит в `src/test/resources/demo-input.txt` и используется тестом консоли.

## Границы ответственности

Модель не зависит от Spring и пользовательского ввода. Контейнер связывает
объекты через конструкторы. `ConsoleMenu` получает готовый сервис парка и потоки;
эти же точки позволяют запускать диалог в тестах без системной консоли.

Добавление транспорта проходит путь: ввод → объект модели → `FleetService`
→ проверка уникальности номера → `ServiceCenter.inspect` → сохранение при допуске
→ вывод решения. Вещь поступает в баланс без техосмотра. Окончание ввода до
создания объекта ничего не меняет на балансе.

Внутри `FleetService` один `LinkedHashMap<String, InventoryItem>`. Он обеспечивает
общую уникальность номеров и порядок вывода. Отчёты строятся по базовому типу
транспорта и интерфейсу потребителя энергии, поэтому не перечисляют его виды.
Отдаваемые списки и итоговый отчёт не дают изменить внутреннее состояние.

## Принятые решения

- Один Gradle-модуль, Java 25, Spring Context, JUnit 5, Mockito, JaCoCo, Checkstyle.
- Состояние хранится только в памяти текущего процесса.
- Обычный велосипед и шлем не реализуют потребление электричества.
- Зарядная станция участвует и в учёте вещей, и в отчёте энергии.
- Прокатный транспорт для новичка имеет простоту от 6 до 10 включительно.
- Номера непустые, общие для всех объектов, сравниваются с учётом регистра.
- Непрошедший техосмотр транспорт отсутствует на балансе; номер не резервируется.
- Для новых видов меняется создание объектов в меню; сервису достаточно
  базовых контрактов. Система регистрации фабрик и слой БД сейчас не нужны.
- При появлении постоянного хранения операции над балансом можно выделить
  из `FleetService`, сохранив его публичный сценарий приёмки.
