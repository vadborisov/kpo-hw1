# ВышКат — ДЗ1 по КПО

Консольное приложение учёта парка: транспорт принимается после техосмотра,
вещи ставятся на баланс сразу. Программа показывает количество объектов,
суточное энергопотребление, транспорт для новичков и весь инвентарный список.
Данные хранятся в памяти одного запуска и не сохраняются после выхода.

## Сборка и запуск

Нужен **JDK 25**. Gradle Wrapper включён в проект; устанавливать Gradle отдельно
не нужно. При первом запуске нужен интернет для загрузки Gradle и зависимостей.

```bash
./gradlew --quiet --console=plain run
```

Для Windows: `gradlew.bat --quiet --console=plain run`.
В IntelliJ IDEA можно импортировать Gradle-проект, выбрать JDK 25 и запустить
`ru.hse.vyshkat.Main`. Приложение читает построчный ввод в UTF-8.

Чтобы получить сборку со скриптами запуска и зависимостями:

```bash
./gradlew installDist
./build/install/kpo-hw1/bin/kpo-hw1
```

Скрипт Windows: `build\install\kpo-hw1\bin\kpo-hw1.bat`.
Архив для передачи можно собрать командой `./gradlew distZip`:
он появится в `build/distributions/`. Для самостоятельной сборки сдаётся исходный
проект с Gradle Wrapper и этим README.

## Меню и правила

1. **Добавить транспорт**: выбрать электросамокат, велосипед или электровелосипед;
   ввести название, номер, простоту, исправность тормозов и рамы. Для электрического
   транспорта дополнительно вводится суточный расход энергии.
2. **Добавить вещь**: шлем либо зарядную станцию. Для станции вводится расход.
3. **Отчёт**: количество транспорта, вещей, всех объектов и общая энергия.
4. **Транспорт для новичков**: принятые устройства с простотой от 6 до 10.
5. **Весь баланс**: названия и инвентарные номера в порядке добавления.
0. **Выход**.

Техосмотр проходит только транспорт. Выбранное нами правило: тормоза исправны
и рама цела. При отказе показывается причина; транспорт не занимает номер и не
попадает ни в один отчёт. Если неисправны оба узла, первой выводится причина
про тормоза. Это учебная модель решения техосмотра по введённым характеристикам.

Имена и номера обязательны; крайние пробелы убираются. Номера уникальны для всего
баланса, сравниваются с учётом регистра, ведущие нули сохраняются. Дубликат
отклоняется до техосмотра, существующий объект остаётся прежним.

Простота — целое число от 1 до 10. Расход — неотрицательное число, допускаются
точка или запятая. Он хранится в `BigDecimal` и суммируется без двоичного
округления. Велосипед и шлем не являются потребителями электричества;
зарядная станция является и вещью, и потребителем. Ответы о состоянии —
`да`/`нет` без учёта регистра либо `1`/`0`.

При неверном значении повторяется запрос поля. При дубликате номера приложение
возвращается в меню. Окончание потока ввода завершает программу без сохранения
незавершённого объекта.

## Демонстрация

Готовая последовательность ввода находится в
[demo-input.txt](src/test/resources/demo-input.txt). Запуск на macOS/Linux:

```bash
./gradlew --quiet --console=plain run < src/test/resources/demo-input.txt
```

Она показывает все пункты меню: отчёты пустого парка, добавление трёх видов
транспорта, отказы из-за тормозов и рамы, добавление обеих вещей, дубликат номера,
итоговые отчёты, неизвестную команду и выход. Тесты дополнительно проверяют
ошибочные значения полей и окончание ввода во время добавления объекта.

Итог: **3 транспортных средства, 2 вещи, 5 объектов и 2 кВт·ч в сутки**.
Новичкам подходят `S-001` с простотой 6 и `E-001` с простотой 10.
`B-001` с простотой 5 остаётся на балансе, но не входит в этот список.
Номера `BAD-001` и `BAD-002` отсутствуют на балансе.

## Архитектура

Один Gradle-модуль на Java 25. Spring Context отвечает за DI, JUnit 5 и Mockito —
за тесты, JaCoCo — за покрытие, Checkstyle — за стиль. Spring Boot и база данных
для текущих требований не понадобились.

- [`model`](src/main/java/ru/hse/vyshkat/model) — неизменяемые данные и инварианты.
  `InventoryItem` задаёт название и номер, `EnergyConsumer` — расход энергии.
  `Transport` и `Equipment` содержат общие данные своих иерархий; конкретные виды
  находятся в подпакетах `transport` и `equipment`. Общие проверки строк и расхода
  вынесены в `ModelValidation`.
- [`inspection`](src/main/java/ru/hse/vyshkat/inspection) — контракт `ServiceCenter`,
  реализация `BasicServiceCenter` и результат с причиной `InspectionResult`.
- [`service`](src/main/java/ru/hse/vyshkat/service) — `FleetService` координирует
  приёмку и формирует отчёты. Единственный `LinkedHashMap` содержит весь баланс,
  поэтому уникальность номеров общая. Списки и `FleetSummary` — снимки данных.
- [`console`](src/main/java/ru/hse/vyshkat/console) — `ConsoleInput` разбирает ввод,
  `ConsoleMenu` ведёт диалог и вызывает сервис.
- [`config`](src/main/java/ru/hse/vyshkat/config/ApplicationConfiguration.java) —
  явная сборка зависимостей через Spring `@Bean`. `Main` открывает контекст,
  получает меню и запускает его.

Доменная модель не зависит от консоли и Spring. Вещи добавляются отдельным методом,
который принимает `Equipment`; передать туда транспорт в обход техосмотра нельзя.
Неисправный транспорт является допустимым объектом до приёмки, и его отклоняет
именно техосмотр. Сотрудники не включены в иерархию инвентарных объектов.

## SOLID и принятые компромиссы

- **SRP**: модель проверяет корректность данных, техосмотр решает вопрос допуска,
  сервис управляет балансом, консоль отвечает за диалог. Парсинг ввода отделён от
  команд меню. Хранение в памяти пока находится внутри `FleetService`:
  для этого размера программы отдельный слой хранения увеличил бы число типов
  без нужной функциональности. При появлении БД эту границу следует выделить.
- **OCP**: `FleetService` работает с базовыми типами и интерфейсами. Новый транспорт
  или потребитель энергии автоматически участвует в соответствующих отчётах.
  Проверок конкретных видов транспорта в сервисе нет.
- **LSP**: все наследники `Transport` сохраняют общие ограничения и одинаково
  передаются в сервис. Обычный велосипед не обещает электрическое потребление,
  поэтому не возвращает фиктивное значение и не бросает исключение из такого
  метода. Наследники `Equipment` совместимы с учётом вещей.
- **ISP**: инвентаризация и потребление энергии разделены. Шлем реализует только
  нужные ему операции, зарядная станция участвует в обоих контрактах.
- **DIP**: `FleetService` получает `ServiceCenter` через конструктор. Конкретный
  техосмотр выбирает конфигурация контейнера, сервис учёта его не создаёт.

**Наиболее явно выражен DIP**: правило техосмотра подменяется и в модульных тестах,
и в настоящем Spring-контексте, без изменения `FleetService`.

**Сознательно ограничен OCP в консольном создании объектов**: пункты видов и их
конструкторы перечислены в `ConsoleMenu`. Новый вид потребует добавить пункт
и запрос его характеристик. Для пяти конкретных видов это понятнее, чем отдельная
система регистрации команд и фабрик. Изменение локально; учёт и отчёты остаются
прежними. Компромисс хранения внутри сервиса также ограничивает строгое разделение
ответственности, но не мешает требуемой подмене техосмотра.

## Как расширять программу

- **Новый транспорт**: наследник `Transport`; при потреблении энергии также
  `EnergyConsumer`. Добавить ввод в меню и тесты. `FleetService` и существующие
  отчёты менять не нужно. Если техосмотр нового вида требует дополнительных
  проверок, потребуется расширить правило или реализацию `ServiceCenter`.
- **Сотрудник**: самостоятельная модель и сервис сотрудников. Наследовать
  `InventoryItem` не нужно, сотрудники не входят в баланс и энергопотребление.
- **Склад запчастей**: для поштучно инвентаризируемой вещи — наследник `Equipment`;
  для партий и остатков — отдельная модель складского учёта. Не следует пытаться
  представить количество одинаковых деталей одним уникальным номером вещи.
- **Постоянное хранение**: выделить операции хранения из `FleetService` и добавить
  реализацию для выбранного хранилища; консоль и контракт техосмотра сохраняются.

## Тесты и проверки

```bash
./gradlew clean check
```

На Windows: `gradlew.bat clean check`. Команда запускает JUnit, Checkstyle для
основного кода и тестов и создаёт отчёт JaCoCo.

- Тесты: `build/reports/tests/test/index.html`.
- Покрытие: `build/reports/jacoco/test/html/index.html`.
- Стиль: `build/reports/checkstyle/main.html` и `test.html`.

Конфигурация Checkstyle использует Sun Conventions с исключениями преподавателя
для документации полей и пакетов; числовые литералы разрешены в сценариях тестов.
Проверки не игнорируют нарушения.

Основные тесты:

- [`InventoryModelTest`](src/test/java/ru/hse/vyshkat/model/InventoryModelTest.java)
  проверяет поля, границы простоты и энергопотребления всех видов объектов.
- [`BasicServiceCenterTest`](src/test/java/ru/hse/vyshkat/inspection/BasicServiceCenterTest.java)
  проверяет четыре сочетания состояния тормозов и рамы и пояснение отказа.
- [`FleetServiceTest`](src/test/java/ru/hse/vyshkat/service/FleetServiceTest.java):
  `acceptsAccordingToInjectedCenter` фиксирует делегирование решения подставленному
  Mockito-объекту через конструктор; `keepsRejectedTransportOutOfFleet` — отсутствие
  отказанного транспорта в отчётах; `selectsBeginnerTransportsAtBoundary` — границу
  5/6; остальные сценарии — номера, энергию и неизменяемость снимков.
- [`ApplicationConfigurationTest`](src/test/java/ru/hse/vyshkat/config/ApplicationConfigurationTest.java):
  `replacesCenterInsideContainer` подставляет тестовый `@Primary`-бин техосмотра
  и доказывает, что контейнер внедрил его в сервис вместо стандартного правила.
- [`ConsoleMenuTest`](src/test/java/ru/hse/vyshkat/console/ConsoleMenuTest.java)
  прогоняет полный сценарий с настоящими сервисами и потоками в памяти,
  ошибочный ввод, точность расхода, ответы о состоянии и окончание потока.

Все тесты независимы от сети, реального ожидания и порядка запуска.

## Использование ИИ

ИИ(Codex) помог настроить окружение, наметить план действий и выбрать архитектуру. Код тоже писался с его частичным использованием.
Полностью ИИшкой были написаны тесты и комментарии к коду по Javadoc, чтобы в проекте было удобно разбираться. 
Для написания кода использовался скилл, в котором указаны инструкции по референсу
на преподавательские работы для более чистого читабельного кода.
Вместе с ИИ обсуждались архитектурные решения, использование SOLID, компромиссы.
